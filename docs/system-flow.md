# Budapest - תיעוד תהליך המערכת

## סקירה כללית

מערכת Budapest היא מערכת לניהול תעודות משלוח עבור חברות בנייה. המערכת סורקת אימיילים, מזהה מסמכים (תעודות משלוח, הזמנות רכש, חשבוניות), מחלצת מהם מידע באמצעות OCR, ומבצעת התאמה תלת-כיוונית (Three-Way Match) בין המסמכים.

```
┌─────────────┐    ┌──────────────┐    ┌──────────────┐    ┌──────────────────┐
│  Gmail API  │───▶│  סריקה וזיהוי │───▶│  OCR + חילוץ │───▶│  התאמה תלת-כיוונית │
│  / תיקיות   │    │   מסמכים      │    │   נתונים     │    │   PO ↔ DN ↔ INV   │
└─────────────┘    └──────────────┘    └──────────────┘    └──────────────────┘
```

## 1. שלב הסריקה (Gmail Scanning)

### טריגרים
| טריגר | מסלול | תיאור |
|--------|--------|--------|
| **אוטומטי** | Cron כל 5 דקות | `gmail-scanner.cron.ts` |
| **ידני** | `POST /gmail/trigger` | לחיצת כפתור בממשק |
| **תיקיות מקומיות** | `POST /gmail/local-scan` | לסריקה מתוך test-data/ |

### תהליך הסריקה

```
1. ניקוי סריקות תקועות
   └── סריקות בסטטוס PROCESSING מסומנות כ-FAILED

2. טעינת הגדרות חברה
   └── בדיקה שה-Gmail מחובר
   └── קריאת scanDaysBack (ברירת מחדל: 7 ימים)

3. שליפת הודעות מ-Gmail
   └── שאילתה: has:attachment after:{epoch}
   └── סינון: דילוג על gmailMessageId שכבר עובדו (dedup)

4. עיבוד כל הודעה
   └── הורדת קבצים מצורפים (PDF / תמונות)
   └── זיהוי סוג מסמך (ראו שלב OCR)
   └── יצירת רשומות במסד הנתונים
   └── עדכון ScanLog (SUCCESS / PARTIAL / FAILED)
```

### זיהוי כפילויות
- **תעודות משלוח**: לפי `noteNumber` + `companyId`
- **הזמנות רכש**: לפי `poNumber` + `companyId`
- **חשבוניות**: לפי `invoiceNumber` + `companyId`
- מסמך כפול נזרק (`DuplicateDocumentError`) ולא נוצר מחדש

### טיפול ב-PDF מרובה עמודים
```
PDF עם עמוד אחד ──▶ זיהוי ישיר של סוג מסמך

PDF עם מספר עמודים ──▶ שליחת כל ה-PDF ל-AI
                        └── AI מזהה: { startPage, endPage, documentType }
                        └── חיפוש "פערים" (עמודים לא מכוסים) ← זיהוי בנפרד
                        └── חילוץ כל מקטע ל-PDF נפרד
                        └── עיבוד כל מקטע בנפרד
```

## 2. שלב ה-OCR (חילוץ נתונים)

### ספקי OCR נתמכים
| ספק | מודל | שימוש |
|------|-------|--------|
| **OpenAI** | GPT-4o | ברירת מחדל |
| **Google** | Gemini 2.0 Flash | חלופה |

### זיהוי סוגי מסמכים
המערכת מזהה 6 סוגי מסמכים:

| סוג | תיאור | פעולה |
|------|--------|--------|
| `delivery_note` | תעודת משלוח | חילוץ מלא + התאמה |
| `purchase_order` | הזמנת רכש | חילוץ מלא + התאמה |
| `invoice` | חשבונית מס | חילוץ מלא + התאמה |
| `order_confirmation` | אישור הזמנה | מטופל כ-PO |
| `credit_note` | הודעת זיכוי | מטופל כ-DN |
| `unknown` | לא מזוהה | נדלג |

### חילוץ תעודת משלוח - לוגיקה מרכזית

**אתגר מרכזי**: הבחנה בין "כמות" (כמות שסופקה) לבין "יתרה למשלוח" (כמות שנותרה) - שניהם נראים דומה בטבלה.

**כללי חילוץ**:
- **ספק** = כותרת המסמך (לוגו/שם בראש)
- **לקוח** = אזור "לכבוד"
- שורות פריטים: מק"ט, תיאור, כמות, מחיר, סה"כ
- סימונים בכתב יד: זיהוי X או קו חוצה (דחייה), הערות בכתב יד

**הגהות אוטומטיות** (הורדת ציון ביטחון):
| בדיקה | קנס | סיבה |
|--------|------|--------|
| כמות > 10,000 | -0.20 | ככל הנראה בלבול עמודות |
| מק"ט עם 9 ספרות | -0.15 | ככל הנראה מספר עוסק |
| דפוס מטא-דאטה | -0.30 | ככל הנראה לא מוצר |
| כמות=1 כשאר עשרוניים | -0.15 | ככל הנראה קריאה שגויה |

### חילוץ חשבונית
- מספר חשבונית: "חשבונית מס" (לא מספר לקוח)
- הפניות צולבות: `poReference`, `deliveryNoteReferences`, `quoteReference`
- בדיקה ב-3 מיקומים: כותרת, בלוק הפניות, שורות פריטים

### חילוץ הזמנת רכש
- **הפוך מת"מ/חשבונית**: הקונה = כותרת, הספק = "לכבוד"
- מספר הזמנה: הסרת סיומות (PO, PD, SO)
- תיאורי שורות: לכידת טקסט מלא (עשוי לגלוש)

## 3. שלב ההתאמה (Three-Way Matching)

### תהליך ההתאמה האוטומטית - 4 פאזות

```
  פאזה 1              פאזה 2              פאזה 3              פאזה 4
┌──────────┐       ┌──────────┐       ┌──────────┐       ┌──────────┐
│ גרף הפניות│ ───▶ │ קיבוץ לפי │ ───▶ │ איחוד    │ ───▶ │ חישוב    │
│ Union-Find│       │ ספק (Fuzzy)│       │ יתומים   │       │ סטיות    │
└──────────┘       └──────────┘       └──────────┘       └──────────┘
```

#### פאזה 1: גרף הפניות (Union-Find)
בונים גרף של כל הקשרים הידועים בין מסמכים:

| קשר | דוגמה |
|------|--------|
| חשבונית → הזמנת רכש | `invoice.poReference` = `po.poNumber` |
| חשבונית → תעודת משלוח | `invoice.deliveryNoteReferences` מכיל `dn.noteNumber` |
| ת"מ → הזמנת רכש | `dn.poReference` = `po.poNumber` |
| הזמנה → ת"מ | `po.deliveryNoteReferences` מכיל `dn.noteNumber` |
| אותו אימייל | מסמכים מאותו `scanLogId` |

אלגוריתם Union-Find מקבץ את כל המסמכים הקשורים ל"רכיב מחובר" (connected component).

**נורמליזציה של הפניות**: הסרת אפסים מובילים, הסרת סיומות (PO, PD, DN, SH, SO, INV).

#### פאזה 2: קיבוץ Fuzzy לפי ספק
מסמכים שלא נמצאו דרך הפניות - מקובצים לפי שם ספק:

```
התאמה מדויקת של supplierId
       │ (אם לא נמצא)
       ▼
התאמה Fuzzy של שם ספק:
  1. שם זהה (exact match)
  2. הכלה (אחד מכיל את השני)
  3. חפיפת מילים ≥ 60% (מילים > 2 תווים)
  4. הסרת סיומות משפטיות (בע"מ, ltd, inc, llc)
```

#### פאזה 3: איחוד יתומים
- מסמכים שנותרו ללא התאמה מחוברים להתאמות קיימות עם אותו ספק
- אם אין ספק תואם - נוצרת התאמה "בודדת" (solo match)

#### פאזה 4: חישוב סטיות (Discrepancies)
```
סוגי סטיות:
┌─────────────────────────────────┐
│ CRITICAL (אדום)                 │
│  • הפרש סכום כולל > 10%         │
│  • הפרש כמות בשורה > 10%        │
│  • הפרש מחיר יחידה > 10%        │
├─────────────────────────────────┤
│ WARNING (צהוב)                  │
│  • הפרש סכום כולל 1%-10%        │
│  • חסרה הזמנת רכש               │
│  • חסרה תעודת משלוח             │
├─────────────────────────────────┤
│ INFO (כחול)                     │
│  • חסרה חשבונית                 │
└─────────────────────────────────┘

סטטוסים:
  MATCHED    = אין סטיות
  DISCREPANCY = יש סטיות
  PARTIAL    = חסרים סוגי מסמכים
  RESOLVED   = סטיה שנפתרה ידנית
```

### התאמת שורות פריטים - 3 פאזות

```
פאזה 0: פידבק היסטורי
   └── שימוש בתיקונים קודמים של המשתמש כ-"אמת"
   └── בניית קבוצות שקילות של תיאורים
   └── matchSource: 'feedback'

פאזה 1: מק"ט מדויק
   └── קיבוץ לפי catalogNumber
   └── התאמה ישירה בין סוגי מסמכים
   └── matchSource: 'catalog'

פאזה 2: התאמה סמנטית (AI)
   └── שליחת פריטים שנותרו ל-AI
   └── AI מתאים לפי: קטגוריית מוצר, מילות מפתח, כמויות
   └── כולל 20 דוגמאות פידבק כ-"למידה"
   └── matchSource: 'ai'

פאזה 2 (Fallback): התאמת תיאור
   └── אם AI נכשל: התאמה לפי תיאור זהה (case-insensitive)
   └── matchSource: 'description'
```

**דוגמאות להתאמה סמנטית**:
- "מברשת לניקוי אסלה + תושבת" (הזמנה) = "מברשת תלויה נמוקס גיזה שחור" (חשבונית)
- "מראה זכוכית + מסגרת" (הזמנה) = "מראה-מסגרת פרופיל 02 אלומיניום" (חשבונית)

### סטטוסים של תעודת משלוח
```
PENDING → PARSED → REVIEWED → APPROVED
                             → REJECTED
         PARSE_FAILED
```

- `MOBILE` - הועלה מנייד
- `MANUAL` - הועלה ידנית

## 5. ממשק המשתמש

### דף הגדרות Gmail
- חיבור/ניתוק Gmail (OAuth)
- בחירת ספק OCR (OpenAI / Gemini)
- הגדרת טווח סריקה (1-90 ימים)
- הפעלת סריקה ידנית
- צפייה בלוגים של סריקות (סטטוס, שגיאות, פרטים)
- ניסיון חוזר לסריקות שנכשלו
- ביטול סריקות תקועות
- סריקה מתיקיות מקומיות (לבדיקות)

### דף פירוט התאמה
**תצוגה תלת-עמודתית**:
```
┌────────────────┬────────────────┬────────────────┐
│   הזמנת רכש    │  תעודת משלוח   │   חשבונית     │
│   (כחול)       │   (ירוק)       │   (סגול)       │
│                │                │                │
│  ספק           │  ספק           │  ספק           │
│  תאריך         │  תאריך         │  תאריך         │
│  סכום          │  סכום          │  סכום          │
│  שורות פריטים  │  שורות פריטים  │  שורות פריטים  │
└────────────────┴────────────────┴────────────────┘
```

**טבלת צימודי שורות**: הצגה של כל הפריטים המותאמים עם badge של מקור ההתאמה
**מודל תיקון**: המשתמש יכול לתקן התאמות שגויות → נשמר כפידבק ללמידה עתידית
**ייצוא ל-PDF**: שמירת פרטי ההתאמה כ-PDF (A4 לרוחב)

## 6. אתגרים מרכזיים וקשיים

### אתגרי OCR
| אתגר | תיאור | הפתרון הנוכחי |
|--------|--------|---------------|
| **בלבול עמודות** | "כמות" vs "יתרה למשלוח" | הנחיה מפורשת ב-prompt + קנס ביטחון |
| **כתב יד** | סימוני X, הערות בכתב יד | זיהוי AI של סימוני דחייה |
| **מסמכים מעורבים ב-PDF** | כמה מסמכים בקובץ אחד | Multi-doc detection + page segmentation |
| **מק"טים ארוכים** | מספרי עוסק בטעות כמק"ט | זיהוי 9 ספרות + קנס ביטחון |
| **עברית** | כיווניות, גופנים שונים | Prompts בעברית + מודלים תומכי עברית |
| **סוגי מסמכים דומים** | ת"מ vs חשבונית vs הצעת מחיר | Prompt מפורט עם קטגוריות ברורות |

### אתגרי התאמה
| אתגר | תיאור | הפתרון הנוכחי |
|--------|--------|---------------|
| **תיאורים שונים** | אותו מוצר בשמות שונים | AI Semantic Matching + למידת פידבק |
| **שמות ספקים לא אחידים** | בע"מ, ח.פ., שמות מקוצרים | Fuzzy matching עם חפיפת מילים ≥60% |
| **מספרי הפניה לא תקניים** | אפסים מובילים, סיומות | נורמליזציה של הפניות |
| **מסמכים חסרים** | חלק מהשלישייה חסר | PARTIAL status + orphan consolidation |
| **סטיות מחירים/כמויות** | הבדלים בין מסמכים | חישוב אוטומטי + סיווג חומרה |

## 8. מה חסר / שיפורים אפשריים

### חסרים קריטיים
- [ ] **דשבורד סטטיסטיקות** - אין מבט-על על מצב ההתאמות, אחוזי הצלחה, סטיות פתוחות
- [ ] **ניהול ספקים** - אין ממשק ייעודי לניהול ספקים, מיפוי שמות, מיזוג כפילויות
- [ ] **התראות** - אין מנגנון התראות על סטיות קריטיות, סריקות שנכשלו, מסמכים חסרים
- [ ] **דוחות** - אין יכולת הפקת דוחות תקופתיים (חודשי/שנתי)
- [ ] **Audit Trail מלא** - אין לוג מלא של כל הפעולות (מי שינה, מה, מתי)
- [ ] **הרשאות משתמשים** - אין ניהול תפקידים (מנהל / צופה / מאשר)

### שיפורים רצויים
- [ ] **Retry חכם** - ניסיון חוזר אוטומטי לסריקות שנכשלו (עם backoff)
- [ ] **Batch operations** - אישור/דחייה של מספר התאמות במכה אחת
- [ ] **חיפוש מתקדם** - חיפוש חופשי במסמכים, סינון לפי טווח תאריכים, ספק, סטטוס
- [ ] **העלאת מסמכים ידנית** - ממשק ידידותי להעלאת מסמכים ללא Gmail
- [ ] **אינטגרציות ERP** - ייצוא/ייבוא ממערכות ERP (Priority, SAP)
- [ ] **Webhooks** - התראות למערכות חיצוניות על אירועים במערכת
- [ ] **מובייל** - אפליקציית מובייל או ממשק responsive לשימוש בשטח
